<p>პლაგინის სახელის კოპირება საკმარისი არ არის. შეიძლება ერთი პლაგინი ფორმას ამუშავებდეს, მეორე კი მის ველებს ინახავდეს, ხოლო მესამე თემის შაბლონს ცვლიდეს. <a href="/pricing">aiWEB-ის პროექტის განხილვისას</a> ასეთი დამოკიდებულებები უნდა გახდეს სამუშაოს მოცულობის ნაწილი.</p>

<h2 id="inventory">შექმენით ფუნქციური ინვენტარი</h2>

<p>ჩამოწერეთ ყველა აქტიური, გამორთული და მორგებული პლაგინი. თითოეულს დაურთეთ:</p>

<ul>
  <li>პლაგინის სახელი, წყარო და გამოყენებული ვერსიის ჩანაწერი;</li>
  <li>რომელ გვერდზე, ფორმაზე ან შაბლონზე მოქმედებს;</li>
  <li>რა მონაცემს ქმნის ან ცვლის მონაცემთა ბაზაში;</li>
  <li>რომელ პლაგინზე ან თემაზეა დამოკიდებული;</li>
  <li>სჭირდება თუ არა ფასიანი ლიცენზია, API გასაღები ან ცალკე ანგარიში;</li>
  <li>რა არის მისი შემცვლელი, თუ ახალ გარემოში აღარ გამოიყენება.</li>
</ul>

<p>ინვენტარი ფუნქციის მიხედვით შეავსეთ. „SEO პლაგინი“ ძალიან ფართო აღწერაა. მიუთითეთ კონკრეტული გამოყენება: canonical, sitemap, schema, redirect, მეტა ველი ან სხვა მოქმედება.</p>

<h2 id="graph">დახაზეთ დამოკიდებულებების გრაფი</h2>

<p>დამოკიდებულება ნიშნავს, რომ ერთი კომპონენტი მეორის გარეშე სწორად ვერ მუშაობს. მაგალითად, ფორმის ბლოკს შეიძლება სჭირდებოდეს ველების პლაგინი, ელფოსტის სერვისი და თემის შაბლონი. გრაფში ისრები დახაზეთ ფუნქციის მიმწოდებლიდან მომხმარებელ კომპონენტამდე და თითოეულ კავშირს დაურთეთ ტესტი.</p>

<p>თითოეულ კავშირს ჩაუტარეთ მინიმუმ <strong>2</strong> შემოწმება: ადმინისტრატორში კონფიგურაციის შენახვა და საჯარო გვერდზე შედეგის ჩვენება. რთულ ნაკადს შეიძლება დასჭირდეს <strong>3</strong> შემოწმება, როცა მას ფორმა, გარე სერვისი და შემდგომი შეტყობინება ერთდროულად იყენებს.</p>

<h2 id="core-dependencies">WordPress-ის პლაგინების დამოკიდებულებები</h2>

<p>WordPress-ის 6.5 ვერსიიდან პლატფორმას აქვს პლაგინების დამოკიდებულებების მხარდაჭერა. ოფიციალური დოკუმენტაციის მიხედვით, დამოკიდებული პლაგინი ვერ უნდა გააქტიურდეს მანამდე, სანამ საჭირო პლაგინი არ არის დაყენებული და აქტიური; აქტიური დამოკიდებულებების მქონე პლაგინის გამორთვასა და წაშლასაც შესაბამისი შეზღუდვები აქვს.</p>

<p>პლაგინის header-ში <code>Requires Plugins</code> ველი დამოკიდებულებებს slug-ებით აღწერს. ეს ჩანაწერი არ ცვლის ყველა პროექტულ შემოწმებას: ვერსიის შესაბამისობა, კონფიგურაცია, თემა, მონაცემები და გარე სერვისი ცალკე უნდა გაიტესტოს. circular dependency-ის ან დაუდასტურებელი აქტივაციის შემთხვევაში release-ს სტატუსი უნდა შეჩერდეს.</p>

<h2 id="activation">აქტივაციისა და დაბრუნების რიგი</h2>

<p>staging-ზე ჩაწერეთ აქტივაციის ზუსტი რიგი. ჯერ მოამზადეთ ასლი, შემდეგ ძირითადი დამოკიდებულება, შემდეგ მომხმარებელი პლაგინი და ბოლოს ფორმა ან გვერდის შაბლონი. თითოეულ ნაბიჯზე შეამოწმეთ ადმინისტრატორის ეკრანი, საჯარო გვერდი, მონაცემის შენახვა და შეცდომის ლოგი.</p>

<p>გამორთვამდე იცოდეთ რა დარჩება მონაცემთა ბაზაში. ზოგი პლაგინი დეაქტივაციისას ფუნქციას თიშავს, ზოგი კი მონაცემს ტოვებს. სრული აღდგენის გეგმა მოიცავს მონაცემთა ბაზისა და ფაილების ასლებს, რადგან ერთი კომპონენტი მეორის გარეშე საიტს ვერ აღადგენს.</p>

<h3 id="licenses">ლიცენზია და ანგარიშები</h3>

<p>პლაგინის ფაილის ქონა არ ნიშნავს, რომ ლიცენზია ან API გასაღები გადმოვიდა. ჩამოწერეთ რომელ ანგარიშს ეკუთვნის ლიცენზია, ვის აქვს განახლების უფლება, სად არის key-ის აღდგენა და რა ფუნქცია შეწყდება გასაღების გარეშე. საკვანძო მონაცემი საერთო ტექსტურ ფაილში არ შეინახოთ.</p>

<p>თუ პლაგინი აღარ ემსახურება მოქმედ ბიზნეს-პროცესს, მისი გადატანა მხოლოდ ჩვევის გამო არ არის საჭირო. გადაწყვეტილება და მფლობელი აუდიტის ცხრილში ჩაწერეთ, ხოლო ალტერნატივა staging-ზე დაამტკიცეთ.</p>

<h3 id="scenario">სცენარი: ფორმის პლაგინის ცვლილება</h3>

<p>წარმოიდგინეთ კომპანია, რომლის ფორმა ერთ პლაგინში ინახება, ელფოსტას მეორე ამუშავებს, ხოლო გვერდის ბლოკს მესამე აჩვენებს. ახალ საიტზე მხოლოდ პირველი პლაგინი გადაიტანეს და ვიზუალური ფორმა გამოჩნდა, მაგრამ შეტყობინება აღარ გავიდა.</p>

<p>დამოკიდებულებების გრაფი ამ პრობლემას წინასწარ აჩენს. გუნდი ადგენს თითოეული კომპონენტის ფუნქციას, ამოწმებს API-სა და ლიცენზიას, staging-ზე აგზავნის კონტროლირებულ ტესტს და მხოლოდ მიღებული წერილის შემდეგ ამტკიცებს cutover-ს. თუ რომელიმე კავშირი ვერ დადასტურდა, პლაგინის გადატანა დასრულებულად არ ითვლება.</p>

<h2 id="limitations">დამოკიდებულებების სიის საზღვრები</h2>

<p>პლაგინების რაოდენობის შემცირება ავტომატურად არ ნიშნავს უფრო სწრაფ ან უსაფრთხო საიტს. შედეგი დამოკიდებულია კოდზე, კონფიგურაციაზე, ჰოსტინგზე, თემაზე, გარე სერვისებზე და შემდგომ მოვლაზე. ერთი staging ტესტი ყველა მომხმარებლის გზას ვერ ამტკიცებს.</p>

<p>WordPress-ის დამოკიდებულებების სისტემა ინსტალაციისა და აქტივაციის ნაწილს ეხმარება, მაგრამ ის არ მართავს ყველა ვერსიის თავსებადობას ან ბიზნესის კონფიგურაციას. ამიტომ ამ სტატიის გეგმა უნდა დაუკავშიროთ <a href="/blog/wordpress-migration-staging-and-cutover-plan">staging და cutover runbook-ს</a>.</p>
